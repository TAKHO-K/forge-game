# P3a 로그 - 리더보드 서버(L1) · 파티원 진도 갱신 · 원형 보스맵(4인 · 6종) · 보스 장판 판정 버그

자율 진행 단계(COMMON.md §7). 지시 원문 = 사용자 프롬프트 + 도중 추가 지시 4건(아래 0-추가).

## 0-추가. 도중에 받은 사용자 지시(원문 요지)

1. 보스전 맵을 지금보다 크고 웅장하게 - 최대 4인 입장을 고려한 4인 전용 맵(6종) + 앞으로 추가될 보스를 고려한 계획(기존 맵 재사용 또는 신규 맵의 크기). → 처음엔 "계획만", 곧이어 **"4인 보스맵 구현까지 가능하다면 거기까지 완료"**.
2. 성능 기준(C3)에 꼭 맞추지 못하더라도, 전체 디자인 · 맵 분위기 · 보스와의 색감 · 지형지물이 어울리면 된다.
3. 에셋은 카툰 그래픽 쪽으로 만들 예정이고 최종 외형에 테두리 선이 생길 확률이 높다 - 이 분위기를 반영. 지형지물로 인한 맵 오류 · 끼임만 없으면 된다.
4. 지형지물 = 이동 경로 · 충돌은 가능(보스 돌진 시 상호작용 · 기절)하지만 유저가 세 번 정도 때리면 깨지는 구조물. 깨지면 파편 이펙트. 자연스러운 구조물이면 된다.

## 가정·결정 로그

1. [0 · 해석] 도중 지시 1("계획만")은 곧이어 온 "구현까지 가능하다면 완료"로 대체 - 6종 맵을 구현하고 새 보스용 규칙은 계획서(`docs/phase/P3a-bossmap-plan.md`).
2. [A · 규칙 자리] 진도 판정은 순수 함수 `shared/LeaderboardRules.evaluateClear`(멤버별 advanced · reason · 파티 기록)로 뺐다 - 서버(CombatResolution)와 검증(가)의 시나리오 표가 같은 함수를 쓴다.
3. [A · 옛 게이트] 25-3 "파티 전원 10% 이상일 때만 전원 클리어 인정" → 사용자 확정 규칙(멤버별)으로 대체. 캐리 방지는 "자기 최고 다음 보스 스테이지만" + "본인 10%"로 그대로 성립. 옛 검증 27-3(나2)의 기대("스탠드인 9% → 본인도 안 오름")를 새 규칙으로 개정.
4. [A · 리더만 갱신] 오른 멤버는 `PlayerProfile.raiseInfiniteBest`로 도달(infiniteBest)도 그 보스 스테이지까지 올린다(지금 스테이지는 그대로) - 파티원이 다음 스테이지로 갈 수 있다. 이동 권한(보스 스테이지는 리더만)은 그대로.
5. [A · 값 분리 · 저장] 도달(infiniteBest = 일반 스테이지 이동 규칙)과 기록(bestBossCleared = 보스 클리어)은 원래 따로 있었다 - 순위 · 기록은 bestBossCleared만 본다. 변환 규칙(개발 계정뿐이라 단순하게): **SAVE_VERSION 34 = 계정 `leaderboardTainted` 신설, 보스 클리어가 하나라도 있는 기존 세이브는 true(기록 제외 - 진도 출처를 가릴 수 없다)**. 값 자체는 옮기지 않는다. `snapshotForDevTools` 백업 대상에 넣었다.
6. [B · 저장소] 시즌별 이름 `ForgeLB_v1[_verify]_s<시즌>_<종류>` - personal(스테이지) · class_<직업>(인코딩) · party(인코딩) · partyDetail(일반 - 멤버 · 직업 · 시간) · cards(일반 - 무기만). 지시의 "직업×보스"는 "직업별 저장소에 보스 스테이지 + 시간을 한 값으로"로 읽었다. "시즌"은 이름의 시즌 번호로 분리(시즌 메타 저장소는 만들지 않았다 - 자동 전환은 L1 밖).
7. [B · 인코딩] value = stage × 10^7 + (10^7 − 1 − 시간(0.1초 단위)) - 최대 3.42 × 10^11 < 2^53. 시간 상한 277.8시간(넘으면 같은 꼴찌 시간). 공식 문서에 정렬 저장소 값 범위가 없어 Studio `_verify` 저장소에 최대값을 쓰고 읽어 실측한다(P3a(나)).
8. [B · 한 스테이지 한 번] 개인 최고는 "다음 보스"로만 오르므로 한 사람의 직업별 기록 시간은 그 스테이지 첫 클리어 시간이다(같은 스테이지 재도전으로 시간을 줄이는 경로는 규칙상 없다). UpdateAsync로 "더 클 때만" 올려 서버 경합에도 내려가지 않는다.
9. [B · 읽기] 순위표 6개(개인 · 파티 · 직업 4)를 90초마다 상위 100 - 분당 목록 4회(1인 서버 한도 7). 내 순위: 캐시(상위 100) 안이면 그 순위, 밖이면 내 값 한 번 읽기 + "100위 밖". 카드는 요청 때 읽고 5분 캐시.
10. [B3 · 이론 최소 시간] 멤버 DPS 상한 = 공격력 × (직업 치명 피해 + 옵션 + 확정 치명 초과) × 공속 최대 버프 2.5 ÷ 평타 쿨 × 여유 12 × 보스 받는 피해 최대(파훼 창 ×1.5) × (1 + 치유사 버프). 여유 12는 스킬 · 다중 타격을 모두 덮는 보수값(설정) - 결정 필요 아님(기록을 막는 쪽이 아니라 불가능한 것만 막는다).
11. [B3 · 제외] Studio 수동 Play = 쓰지 않음 · 검증 모드 = `_verify` 저장소 · 라이브 UserId ≤ 0 · 제외 목록 · `/gg` 사용 계정(채팅 명령 처리 첫 줄에서 표시). 스탠드인(테이블)은 쓰지 않는다.
12. [C · 반경] 120(옛 정사각형 반폭 96). 이유 = 면적 +23% · 4인 분산. 파동 최대 반경은 옛 값(96 × 1.464 = 140.6)을 데이터로 고정 - 처치 시간 모형(29-2 기대값 5종 × 6값)이 반경 96 / 120에서 소수점까지 같다(하네스).
13. [C · 킷] 전갈 여왕 유사 웅덩이 ±87 → ±111(돌진 정지점 115를 덮는 같은 뜻) · 폐허 기둥 = 벽 안쪽 고리. 심해 군주 돌단 4곳 → **8곳(반경 65)** - 원 안 어디서든 가장 가까운 단까지 54.7(옛 56.6 · 회피 57). 4곳이면 약 73으로 범람 회피 부등식이 깨진다. 중심 단은 보스 스폰과 겹쳐 뺐다. 29-4 검증의 "단 4곳" 고정 기대를 데이터(단 개수) · 원 안 격자로 개정.
14. [C2 · 벽 여백] 대상 원(낙석 · 낙빙 · 독침)의 중심을 벽 안쪽으로 누르는 여백 2 → 0(원형 아레나만 - 데이터 `circleTargetMarginStuds`). 하네스(2,000회): 원 반경 120 · 벽 1stud에서 여백 2 = 3/48 실패 · 1 = 1/48 · 0 = 0/48. 0이어도 첫 원은 대상 발밑이다(몸 반폭 1).
