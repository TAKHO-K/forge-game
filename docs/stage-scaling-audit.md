# S21a 고스테이지 수치·경제 감사

읽기 전용 점검 보고서. 게임 코드·수치는 이 세션에서 수정하지 않았다. 표본 대조는 Studio Play +
`execute_luau`로 실제 게임 모듈(`InfiniteStage`·`MonsterData`·`BossRules`·`BalanceSim`·`Option`·
`CharacterLevel`)을 직접 불러 계산했다(코드를 고치지 않고 읽기·실행만 했다).

## 표시 규칙

- **[코드]** = 코드 공식에서 직접 계산(파일·줄 명시). 이번 감사는 대부분 여기 해당한다 - 표본은
  Studio에서 실제 게임 모듈을 그대로 호출해 검산했다(손 계산이 아니다).
- **[가정]** = 플레이어 모델이 필요한 값. 가정을 표 아래 전부 명시하고 민감도를 붙인다.
- **[없음]** = 코드에 그 공식·기능이 없음. 추정해서 채우지 않았다.
- 판단·권고는 하지 않는다. 예외: 2번 판정 O/주의/X, 4번 지배 전략 판정, 5c "조건을 만족하는 범위 보고".

## 0. 설계 한계 vs 실제 한계

### 0-1. 정상 진행으로 갈 수 있는 최대 스테이지 [코드]

`server/StageServer.server.lua:53-70`이 이동을 검사하는 유일한 곳이다:

```
local best = PlayerProfile.getInfiniteStageBest(player)
if targetStage < 1 or targetStage > best + 1 then
    reject(player, "range")
end
```

위쪽 상한은 **`본인 최고 도달 스테이지 + 1`뿐**이다. 그 값 자체에 상한이 없다 - `PlayerProfile.
setInfiniteStage`(`server/PlayerProfile.lua:488-500`)도 `PlayerProfile.setInfiniteStageDirect`
(`:1417-1428`)도 숫자를 clamp하지 않는다. 즉 **코드에는 "여기서 막힌다"는 숫자가 없다** - 보스를
계속 깨면(15-1 게이트, 아래) 이론상 무한히 올라간다. "설계 한계"는 강제 정지선이 아니라 **부동소수
정밀도가 깨지는 지점**(0-3)이다.

### 0-2. 12000을 본 경로 [코드]

두 경로가 있고 **둘 다 정상적으로 존재한다**(하나만 있는 게 아니다):

1. **디버그 명령** - `/gg stage <n>`(`server/DevTools.server.lua:1048, 1241-1243` →
   `PlayerProfile.setInfiniteStageDirect`). 도움말 문구 그대로 "생존타수/보상 배율 계산용, 물리적
   이동 아님" - Studio 허용 목록(`isAllowed`) 계정만 즉시 임의의 스테이지 값을 프로필에 박을 수
   있다. 배포판(허용 목록 밖 계정)에서는 이 명령 자체가 조용히 무시된다(§0-1과 동일한 `isAllowed`
   검사, `DevTools.server.lua:2276-2278`).
2. **정상 진행(그라인딩)** - 0-1의 `best+1` 규칙에는 상한이 없으므로, 보스를 계속 깨면서 시간을
   들이면 이론상 도달 가능하다. 코드가 막지 않는다는 뜻이지 실제로 그렇게 플레이한 사람이 있다는
   기록은 없다(세이브에 그런 흔적이 있는지는 이번 감사 범위 밖 - DataStore를 열람하지 않았다).

### 0-3. 이중정밀도(double) 붕괴 지점 - PRD 문서값 vs 실제 코드값

PRD 20.9-1은 웹 이식 초기 가정(스테이지1 보스체력 38,896)으로 **"스테이지 ≈4,853에서 몬스터 HP가
inf"**라고 적어 뒀다(`PRD-forge-game-roblox.md:946-954`). 그런데 실제 로블록스 코드는 그 값을
그대로 안 쓴다 - `InfiniteStageConfig.lua` 주석대로 base는 `MonsterData.tier1`의 실제 검증값
(hp=80)이고 보스는 거기에 `BossData` 배율(20)과 파티 인원 배율(N^p)을 추가로 곱한다. 그래서
**실제 코드로 재현하면 지표마다 붕괴 스테이지가 조금씩 다르다** - 아래는 Studio에서
`InfiniteStage.getMonsterHp/getMonsterAttack/getGoldReward`와 `BossRules.buildInstanceData`를
직접 이분 탐색으로 호출해 얻은 값이다(추정이 아니라 실행 결과):

| 지표 | inf가 되는 첫 스테이지 | 근거 |
|---|---|---|
| 잡몹(tier1) HP | **4,897** | `InfiniteStage.getMonsterHp` |
| 잡몹(tier1) 공격력 | **4,913** | `InfiniteStage.getMonsterAttack` |
| 잡몹(tier1) 골드 | **4,915** | `InfiniteStage.getGoldReward` |
| 보스 HP(1인) | **4,876** | `BossRules.buildInstanceData(.., 1).hp` |
| 보스 HP(4인) | **4,871** | `BossRules.buildInstanceData(.., 4).hp`(파티 배율이 먼저 넘긴다) |
| 최대체력 보너스(itemLevel=stage 가정) | **4,905** | `CombatConfig.maxHpBonusBase × CharacterLevel.getItemLevelMultiplier` |
| 방어력 보너스(itemLevel=stage 가정) | **4,944** | `ArmorData.baseDefense × 등급배율 × CharacterLevel.getItemLevelMultiplier` |

**결론: "설계 한계"는 정확히 한 숫자가 아니라 4,871 ~ 4,944 사이에 몰린 구간이다.** 사용자 기억의
"4,900"은 이 구간의 대표값으로 정확하다. PRD의 4,853은 그 시절 가정값(38,896 base)으로 계산한
근사치라 실제 코드값(구간 하한 4,871)과 약 0.4% 차이 - 같은 자릿수, 같은 결론(둘 다 k=1.155
성장률에서 나온 필연적 결과)이라 재검증할 필요는 없지만, **본문의 정확한 숫자는 이 표를 기준으로
쓴다.**

### 1-2. inf·nan·음수·정수 정밀도 [코드, Studio 실측]

**정수 정밀도 2^53(9,007,199,254,740,992) 초과 - inf보다 훨씬 먼저, 훨씬 조용히 온다:**

| 값 | 2^53 초과 스테이지 |
|---|---|
| 잡몹(tier1) HP | 226 |
| 잡몹(tier1) 골드 | 244 |
| 잡몹(tier1) 경험치 | 252 |
| 잡몹(tier6·드래곤) HP | 206 |
| 잡몹(tier6·드래곤) 골드 | 224 |
| 보스 골드(1인) | 223 |
| 보스 HP(1인) | 205 |

Luau number는 IEEE754 double이라 정수도 2^53을 넘으면 더 이상 "정확한 정수"가 아니다(가장 가까운
표현 가능한 값으로 반올림). **스테이지 200 ~ 250 사이부터 골드·HP·경험치가 더 이상 정확한 정수가
아니다** - 충돌·에러는 없고 상대오차도 극히 작지만(~10⁻¹⁶), "정확히 이 값만큼 차감"류의 등식 비교가
전제라면 이 구간부터 이론적으로 어긋날 수 있다. 실제 소비 경로(강화 골드 차감 등)는 뺄셈 결과가
0인지 확인하는 방식이 아니라 "충분한지" 비교(`trySpendGold`)라 실사용 피해는 낮다.

**inf가 실제로 만드는 결과 - 스테이지 순서대로:**

1. **스테이지 ≈2,448 [코드, 버그] - 측정 도구(BalanceSim)만 먼저 깨진다.**
   `shared/BalanceSim.lua:170`의 생존 타수 공식이 `alpha * A * A`(공격력의 **제곱**)를 직접
   계산한다. `A²`는 `A` 자신보다 훨씬 일찍 오버플로한다 - `A > sqrt(1.7977×10³⁰⁸) ≈ 1.34×10¹⁵⁴`면
   `A²`가 이미 inf다. tier1 공격력이 이 값을 넘는 스테이지가 **2,448**(Studio 실측: 2,000에서
   survive=7.00, 2,500에서 survive=0.00·dmgPerHit=inf로 재현). **이건 실제 게임의 버그가 아니라
   `/gg measure`·`/gg curve`(밸런스 측정 도구) 자체의 부동소수 결함이다** - 실제 몬스터→플레이어
   피해 계산(`server/PlayerDamage.lua:38`)은 `defense / (defense + alpha*attack)`로 **제곱을 안
   만든다**(수학적으로는 같은 식이지만 연산 순서가 달라 오버플로 시점이 다르다). 게임 자체는 이
   지점에서 안 깨진다 - 측정 도구의 보고만 스테이지 2,448부터 신뢰할 수 없다.
2. **스테이지 ≈4,871 ~ 4,915(0-3 표) - 진짜 게임이 깨지기 시작.** 공격력·HP·골드가 순서대로
   `inf`가 된다.
3. **스테이지 ≈4,913 ~ 4,943 사이 - "즉사" 구간.** 몬스터 공격력이 먼저 inf가 되고(4,913) 플레이어
   방어력은 아직 유한할 때(방어력 붕괴는 4,944), `PlayerDamage.computeHitDamage`의
   `reduction = D/(D+inf) = 0` → `dmg = A×(1-0) = inf`. **어떤 공격이든 무조건 한 방에 죽는다**
   (크래시는 아니다 - `math.max(hp - inf, 0) = 0`로 정상 처리된다).
4. **스테이지 ≥ 4,944 - `NaN` 오염, 영구 고장.** 공격력·방어력이 둘 다 inf가 되면
   `reduction = inf/inf = NaN`, `dmg = NaN`. Studio에서 직접 확인: Luau의
   `math.max(NaN, 0)`는 **`NaN`을 그대로 돌려준다**(`0`이 아니다). 즉
   `PlayerDamage.takeDamage`의 `newHp = math.max(hp - NaN, 0)`가 **`NaN`으로 고정되고, `NaN`은
   이후 어떤 연산(자동회복 포함)을 거쳐도 계속 `NaN`이다** - 그 플레이어의 HP가 영구히 고장 난다
   (서버 재시작이나 프로필 수정 없이는 회복 불가능한 상태로 추정 - 이번 감사에서 실제로 그 상태의
   플레이어를 만들어 재접속까지 확인하지는 않았다).
5. **스테이지 ≥ 4,897(잡몹 HP inf 시점) 이후 - 화면 표시 자체가 멈출 수 있다(무한 루프).**
   `shared/NumberFormat.lua:68-91`의 `NumberFormat.format`은 `while scaled >= STEP do scaled =
   scaled / STEP end`로 큰 수를 K/M/B/두 글자 단위로 줄인다. **`scaled`가 `inf`면 `inf/1000`도
   `inf`라 이 루프가 절대 끝나지 않는다** - Studio에서 `math.floor(math.huge)`부터 20회 반복까지
   직접 실행해 확인(값이 계속 `inf`로 고정, 종료 조건이 성립하지 않음). 골드 HUD(`GoldHud.
   client.lua`)·체력바(`PlayerHealthBar.client.lua`)·데미지 숫자(`DamageNumbers.lua`)가 전부 이
   함수를 쓴다 - `inf`가 된 값을 표시하려는 순간 그 스레드가 멈추고, 로블록스의 스크립트 타임아웃
   watchdog이 몇 초 뒤 강제 종료할 때까지 그 UI 갱신이 멎는다(전체 서버 다운은 아니다 - 그
   스레드만 죽는다). **`NaN`은 이 루프에 안 걸린다**(`NaN >= 1000`이 항상 false라 루프를 아예
   안 돈다 - 대신 `%.1f` 포맷터가 `"nan"` 문자열을 그대로 찍는다).

**요약 - 스테이지가 오르며 처음 깨지는 순서**: ① 200 ~ 250: 정수 정밀도 조용히 소실(체감 없음) →
② 2,448: 측정 도구(`/gg measure`)만 오작동, 실제 게임은 무사 → ③ 4,871 ~ 4,915: 실제 수치가 `inf`
전환 시작 → ④ ~4,913부터: 화면 표시 무한 루프 위험 → ⑤ ~4,913 ~ 4,943: 무조건 즉사 → ⑥ ≥4,944:
`NaN` 영구 오염.

**표시 포맷(K/M/B/두 글자) 붕괴** [코드, PRD 인용]: `NumberFormat.lua`는 K/M/B/T(10³~10¹²) 뒤
두 글자 코드(aa~dz, `TWO_LETTER_FIRST`를 a~d로 제한)로 넘어간다. PRD 20.9-1은 "이중정밀도 자체가
스테이지 ≈4,853에서 깨지므로 세 글자(`aaa`, 스테이지 ≈5,150부터 필요)는 double이 이미 죽은 뒤에나
등장한다"고 적어 뒀다 - 코드의 `longCode` 분기가 실제 유효 스테이지 범위 안에서는 **호출될 일이
없다**는 뜻(세 글자 이상 표기 자체가 죽은 코드 경로에 가깝다). 위 ⑤ 무한 루프는 이 세 글자 분기
이전, 값 자체가 `inf`가 되는 순간 발생하므로 이 붕괴보다 먼저 온다.

**UI 칸 넘침(계산)** [가정]: 텍스트 라벨의 실제 픽셀 폭 측정은 이번 감사 범위 밖(Studio 캡처 필요,
"필요할 때만 Play" 원칙에 따라 생략) - 대신 문자열 길이만 보면 두 글자 코드 구간(`"658.1ag"`류,
최대 7~8자)까지는 기존 강화 골드 표시(`"624,000,000"`류, 11자)보다 오히려 짧다. **UI 폭 자체는
문제가 아니고, 문제는 값이 `inf`가 되는 순간 그 문자열 생성이 끝나지 않는다는 것(위 ⑤)이다.**

**DataStore·OrderedDataStore 저장 범위** [없음]: 리더보드용 `OrderedDataStore` 사용 코드는
저장소 전체에 **없다**(`grep OrderedDataStore` 결과 0건) - 향후 세션에서 신설해야 하는 항목이다.
현재 `DataStoreService`(`SaveConfig.dataStoreName`)는 스테이지·골드를 평범한 Lua number로
저장한다. 정수 표현 한계는 위 "2^53 초과" 표와 동일하게 적용된다(저장 자체가 별도로 값을 더
손상시키지는 않는다 - 이미 메모리 위에서 겪은 정밀도 손실을 그대로 실어 나를 뿐). `OrderedDataStore`

## 4. 몬스터·드랍 "선택지" 검증 (사냥 구역 tier 기준)

### 4-1. 설계 확인 [코드]

**핵심 발견 - 사용자가 상정한 "낮은 tier 드래곤" · "높은 tier 슬라임"은 코드에 존재하지 않는다.**
`shared/data/MonsterData.lua:112-119`의 `TIER_INFO`는 tier 1~6에 **종 하나씩만** 고정 배정한다
(tier1=슬라임 … tier6=드래곤). `shared/data/WorldConfig.lua:62-75`도 맵의 9개 구역을
tier1~6 + 강화소 + 리스폰 + 커뮤니티로 1:1 배치한다(Studio 콘솔 실측: "9개 구역, tier 몬스터 54마리
스폰"). **"드래곤이 낮은 tier 구역에도 나온다"거나 "슬라임이 높은 tier 구역에도 나온다"는 경로 자체가
없다** - 종과 tier가 정확히 1:1이다. 사용자가 설계에서 상정한 "몹 종류 선택"은 **설계 없음**이다.

대신 tier 내부에 존재하는 "강도 선택지"는 **접두사 변종**(`shared/data/MonsterPrefixData.lua`) -
Studio 콘솔 실측: 연약한(frail) HP×0.50/보상×0.50, 단단한(sturdy) HP×2.00/보상×2.00, 거대한(giant)
HP×3.00/보상×3.00 - 셋 다 시간당보상이 정확히 1.0000으로 동일(공정성 검증 통과). 이건 "몬스터
선택"이 아니라 "같은 구역 안에서 무작위로 섞여 나오는 변형"이라 사용자 의도(같은 구역에서 어떤 몹을
때릴지 스스로 고른다)와는 다른 축이다.

**tier 간에는 이미 시간당 보상이 완전히 동일하도록 설계돼 있다** - Studio 콘솔의 자체 공정성
검증(`MonsterData.fairnessCheck`)이 tier1~6 전부 "시간당보상=1.3053"으로 정확히 같음을 서버
시작마다 자동 확인한다(`MonsterData.lua:16-28`의 공식 그대로). 즉 "구역 선택 자체는 지배 전략이
없다"가 **설계·자체 검증 양쪽에서 이미 보장돼 있다.**

### 4-4. 파티 1인당 효율 [코드]

**보스**: `BossRules.partyHpExponent()`(p≈0.4799)로 4인 파티 처치 시간 = 솔로의 `4^(p-1)`=0.499배
(2배 빠름). 보상은 4인 전원이 각자 독립 1인분(§5-2) - **1인당 효율 = (전체 처치 속도 2배) ÷
(인원 4) = 솔로의 0.5배**다. 이건 "파티가 손해"가 아니라 **설계가 의도한 정확한 절반**(파티
정원이 진행을 앞당기는 폭이 "보스 한 칸을 넘지 않게" 유도한 `BossRules.lua:20-35` 주석의 직접
결과) - 판정 기준(1인당 효율 < 솔로 = X)으로 보면 **X**이지만, 이건 리더보드 축("최고 도달
스테이지")의 의미를 지키기 위한 **의도된 설계**라고 코드 주석이 명시한다.

**일반 몹(공유 HP 사냥터)**: 보상 분배가 잡몹과 완전히 같은 규칙(기여 10% 이상 전원, 나눠 갖지
않음, §5-2)이라 **파티는 골드·경험치·드랍을 전혀 나누지 않으면서 처치 속도만 합산 DPS로 빨라진다**
- 4인이 동시에 같은 몹을 때리면 그 몹은 1인일 때보다 훨씬 빨리 죽고, 죽었을 때 기여 10%를 넘긴
전원이 각자 온전한 1인분을 받는다. **1인당 효율은 솔로보다 명백히 높다**(정확한 배수는 "각자
얼마나 때렸는가"에 달려 있어 이번 감사에서 배수를 확정하지 않았다 - [가정] 필요 항목: 4인이 균등하게
때린다면 몹이 죽는 속도가 약 4배가 되고, 그 사이 각자 기여 10% 문턱은 쉽게 넘으므로 1인당 골드/분은
솔로 대비 크게 증가한다). **판정 기준(1.5배 초과 = 주의)에 비춰 보면 주의~X 쪽**이지만 정확한
배수는 "몇 명이 어떤 비율로 때리는가"라는 가정에 의존한다.

## 5. 보석 레벨 · 일반 몹 드랍 자격

### 5-1. 보석 레벨 [코드]

- **이미 itemLevel 필드가 있다.** `shared/Gem.lua:55-58`의 `Gem.buildGrantedGem`이 환생 지급
  보석에 `itemLevel`을 저장하고(호출부 `PlayerProfile.rebirth`가 "환생 순간 캐릭터 레벨=25×회차"를
  넘긴다), `server/PlayerProfile.lua:657`의 `dismantleItem`이 분해할 때
  `{ grade, itemLevel = item.itemLevel, option }`으로 **원본 장비의 itemLevel을 그대로 보석에
  옮긴다.** 장비의 itemLevel은 `Loot.rollItemLevel(stage, delta)` = "잡은 스테이지 ± 삼각분포
  델타"(`shared/Loot.lua:44-46, 95-97`)다. **몬스터에 별도 "레벨" 필드는 없다** - 이 게임에서
  "몬스터 레벨"에 대응하는 값은 사실상 "그 몬스터를 잡은 스테이지"뿐이다. 즉 사용자가 제안한
  "보석 레벨 = 몬스터 레벨"은 **이미 구현돼 있다**(itemLevel = dropStage±2, 사용자 제안의
  "상한 없음"도 이미 그대로 - `Loot.rollItemLevel`에 상한이 없다).
- **리롤 옵션 범위는 이 itemLevel을 실제로 읽지만, 레벨125에서 얼어붙는다.** `shared/Option.lua:
  22-34`의 `Option.levelFactor(level)`:
  `f(L) = (1 + 0.06×(min(L,125)-1)) / (1 + 0.06×99)` - **`min(L,125)`로 125 이후 완전히
  동결**된다. Studio 실측(`Option.rangeOf("attackPercent","primordial", itemLevel, nil)`):

  | itemLevel | levelFactor | 옵션 값 범위(min/mid/max) |
  |---|---|---|
  | 1 | 0.1441 | 0.038 / 0.043 / 0.049 |
  | 25 | 0.3516 | 0.092 / 0.106 / 0.119 |
  | 100(기준) | 1.0000 | 0.263 / 0.300 / 0.338 |
  | 125 | 1.2161 | 0.319 / 0.365 / 0.410 |
  | **500** | **1.2161(동일)** | **0.319 / 0.365 / 0.410(동일)** |
  | **1000** | **1.2161(동일)** | **동일** |
  | **4853(설계 한계)** | **1.2161(동일)** | **동일** |
  | **12000** | **1.2161(동일)** | **동일** |

  **레벨(=몬스터 레벨) 125 이후로는 itemLevel이 아무리 커져도(500이든 12000이든) 옵션 값이
  완전히 똑같다.** 숫자 안전성은 **완벽하다**(고정값이라 오버플로 자체가 불가능) - 다만 "몬스터
  레벨이 높을수록 보석이 세진다"는 사용자의 설계 의도와는 **지금 정면으로 어긋난다**: itemLevel
  12000짜리 보석과 itemLevel 125짜리 보석의 옵션 값은 코드상 완전히 동일하다. 이건 버그가 아니라
  `FREEZE_LEVEL`(`Option.lua:26`, `CharacterLevelConfig.killTargetAnchors`의 마지막 앵커=125)이
  의도적으로 정지시킨 것 - 애초에 이 값이 "캐릭터 레벨"(환생 5회째 상한)을 위해 설계된 상수를
  그대로 재사용하고 있어서, 몬스터 스테이지(무한)와는 애초에 다른 축의 값이다.
- **같은 구간 몬스터 HP 성장률과 비교**: 몬스터 HP는 itemLevel 125 이후로도 계속 `k=1.155`로
  크는데(1-1 표), 옵션 값은 멈춰 있다. 즉 **"보석의 전투력 기여 비율"은 스테이지가 오를수록
  상대적으로 0에 수렴한다** - 이게 바로 재설계가 필요한 지점이다(6-3의 곡선 결정으로 넘김).
- **S02-1 itemLevel 불변식과의 관계** [없음 - 확인 못함]: S02-1이 정확히 어떤 불변식인지
  README(S02 줄, 미결 "단계2 isValidProfile 불변식 미결")만으로는 식 전체를 재현할 수 없었다 -
  `PlayerProfile.lua`에 `isValidProfile` 함수 자체가 존재하는지 이번 감사에서 별도로 찾지 않았다
  (범위: 밸런스·경제 감사이지 세이브 마이그레이션 감사가 아니다). **[없음]**으로 남긴다.
- **재설계 입력 데이터(요청 그대로)**:

  | 몬스터 레벨(=itemLevel) | 태초 등급 옵션 값 범위(min/mid/max) | 몬스터 HP(tier1 기준) |
  |---|---|---|
  | 100 | 0.263 / 0.300 / 0.338 | 1.255×10⁸ |
  | 500 | 0.319 / 0.365 / 0.410(125에서 동결) | 1.354×10³³ |
  | 1000 | 동일 | 2.645×10⁶⁴ |
  | 4853(설계 한계) | 동일 | 3.555×10³⁰⁵ |
  | 12000 상당 | 동일(계산 불가 지점 - HP는 이미 inf) | inf |

  **전투력 기여 비율**: `attackPercent` 옵션(위력) 1개의 값이 최대 0.410(+41%)로 고정인 반면,
  같은 구간 몬스터 HP는 스테이지당 ×1.155씩 무한히 큰다 - itemLevel=500에서 이미 "보석 하나가
  주는 %"는 그 스테이지의 필요 전투력 대비 무의미한 수준으로 작아진다(정확한 상대 기여도는
  플레이어의 총 공격력 구성에 달려 있어 [가정] 필요 - 곡선 자체 재설계는 이 보고서 범위 밖).
  **숫자 안전성**: 상한 없이 12000까지 가도 절대 깨지지 않는다(값이 얼어붙어 있으므로) - 이 점은
  재설계 시 그대로 상속해도 안전하지만, 상속하면 "레벨이 오를수록 세진다"는 설계 의도를 못
  살린다는 뜻이기도 하다.
- **세이브 영향** [코드]: `itemLevel` 필드는 이미 존재하므로(장비·보석 공통) **새 필드가
  필요 없다** - 옵션 값 계산 공식(`Option.levelFactor`)만 바꾸면 된다. `SAVE_VERSION`을 올릴
  필요도 없다(기존 값을 다시 읽는 방식만 바뀌지, 저장 스키마는 그대로).

### 5-2. 일반 몹 드랍 자격 [코드]

- **판정 기준: 데미지 비율, 막타 아님.** `server/AttackServer`/`MonsterState.applyDamage`
  (`server/MonsterState.lua:264-269`)가 `ratioDealt = damage / effectiveMaxHp`를 플레이어별로
  누적하고, 몬스터가 죽으면 `CombatConfig.contributionRewardThreshold`(**0.10 = 10%**,
  `shared/data/CombatConfig.lua:103`) 이상 누적한 **전원**이 각자 독립적으로 골드·경험치·드랍을
  받는다(`server/CombatResolution.lua:190-236`, 나눠 갖지 않는다). **사용자의 "데미지 10% 미만이면
  보상 없음" 기억이 정확하다.** PRD에도 같은 규칙(19-4 [2], C안)이 기록돼 있어 **PRD-코드 불일치
  없음.**
- **파티 안에서 개별 vs 공유**: 파티 여부와 무관하게 **전원 개별 판정**이다 - 파티원이든 남남이든
  같은 몬스터를 때린 모든 플레이어가 똑같이 "내 기여 비율 ≥10%"만 본다. 파티라서 특별히 공유되거나
  나눠지는 로직은 없다(위협·타겟팅도 공유 HP 자체가 이미 여러 명을 허용하므로 별도 파티 분기가
  필요 없다).
- **효과적 최대체력이 "공격자 본인의 스테이지" 기준이라는 게 핵심 변수다.** `effectiveMaxHp =
  InfiniteStage.getMonsterHp(entry.data.hp, attackerStage)` - **몬스터의 절대 HP가 아니라
  "이 몬스터가 공격자 자신의 스테이지라면 가졌을 HP"로 각자 다르게 계산한다.** 이게 §4c/§5c와
  직결된 저레벨 버스 분석의 핵심이다(아래).
- **보스 보상 자격도 동일한 임계값 코드다.** `server/CombatResolution.lua:190-236`의
  `handleBossDeath`가 `BossEncounter.getMembersOfModel(target)`(그 보스 encounter에 참가한
  파티원 전원)을 후보로 놓고 똑같이 `contributions[member] ≥ 0.10`으로 거른다. **주석 문서
  (`MonsterState.lua:273-275` "보스는 항상 빈 테이블 - 애초에 기록하지 않는다")는 오래된
  설명이고 실제 코드(`MonsterState.lua:219-230`, 24-1에서 추가)는 보스도 기록한다** - 코드와
  주석이 어긋나는 사례를 하나 더 확인했다(판단 없이 사실만 기록 - 24-1 세션 노트에 이미 있을 수
  있으니 별도 수정은 이 세션 범위 밖). **다만 보스는 잡몹과 계산 기준이 다르다**: 잡몹은
  `attackerStage`(공격자 자신) 기준으로 매번 effectiveMaxHp를 다시 계산하지만, 보스는
  `damage / entry.maxHp`로 **보스의 실제(절대) 최대체력** 하나만 쓴다(`MonsterState.lua:227-228`).
  즉 **보스 기여 10% 문턱은 잡몹보다 훨씬 엄격하다** - 저스탯 플레이어가 고스테이지 보스에서
  진짜 원본 데미지의 10%를 넣는 건 거의 불가능하지만, 같은 플레이어가 고스테이지 잡몹에서는
  "내 스테이지 기준 HP"의 10%를 훨씬 쉽게 채울 수 있다(아래).

- **치유모드 치유사의 드랍 수령 비율** [코드 사실 + 논리적 귀결, 가정 최소]: 치유모드(Q, 순수
  회복 - `SkillData.healer.Q`)는 데미지를 만들지 않는다. 기여 판정이 오직 "이 몬스터에 낸 데미지 /
  effectiveMaxHp"이므로, **한 몹이 죽는 동안 줄곧 Q만 쓴 치유사는 그 몹에서 기여 0%**다 - 파티냐
  아니냐와 무관하게 보상을 못 받는다(코드에 "파티원이라 예외" 조항이 없다). 딜링모드(E)로 전환해
  때린 시간만큼만 기여가 쌓인다. 저tier 잡몹은 처치 시간이 2 ~ 5초로 짧아(§4-3 표) 치유사가 그
  사이 잠깐이라도 때리지 않으면 그 개별 몹에서는 100% 보상 제외 - **정확한 "받는 비율"은 그
  치유사가 시간의 몇 %를 딜링모드로 쓰는가에 달려 있어 [가정] 없이는 퍼센트를 못 낸다**(이
  비율 자체는 코드에 없다 - 플레이 스타일 변수).

- **저레벨 유저가 고레벨 파티를 따라다닐 때** [코드 + 논리적 귀결]:
  1. **자격 취득은 오히려 쉽다.** 잡몹의 기여 비율은 "공격자 자신의 스테이지 기준" HP로 계산되므로,
     저레벨 유저의 미미한 절대 데미지도 자기 기준으로는 상대적으로 큰 비율이 된다 - 정상적인
     "내 레벨에 맞는 사냥"과 판정 계산식이 완전히 동일하다(스테이지가 자기 것이면 계산도 자기
     것). 즉 **파티의 고레벨 몹을 때리는 저레벨 유저는 평소 자기 레벨 사냥과 비슷한 감각으로
     10% 문턱을 넘길 수 있다.**
  2. **하지만 itemLevel(파워)은 여전히 낮다.** `dropStage = recipientStage`(그 몹은 보스가
     아니므로) - 드랍되는 장비의 itemLevel은 **"잡은 사람 자신의 스테이지"**이지 파티나 몹의
     스테이지가 아니다(`CombatResolution.lua:113`). 등급 분포(tier表)는 그 구역의 tier를 따르므로
     상위 등급(태초 포함)이 나올 확률 자체는 고tier 구역 몹을 잡을 때와 같지만, **나온 태초의
     itemLevel은 저레벨 유저 자신의 낮은 스테이지에 고정**돼 실전력은 약하다.
  3. **보스는 반대다.** 보스 드랍의 itemLevel은 `monsterData.stageNumber`(보스 스테이지, 전원
     동일)이므로 저레벨 파티원이 보스 처치 기여 10%(절대 HP 기준, 훨씬 엄격)를 넘기기만 하면
     **고레벨 itemLevel 그대로**의 태초를 받는다 - 다만 이 문턱은 위에서 설명한 잡몹보다 훨씬
     높다(같은 스테이지 잡몹 대비 원본 값 자체가 절대 기준이라).
  - **결론(계산 없이 코드 사실만)**: "잡몹 버스"는 **자격은 쉽지만 전리품 파워는 약하다**,
    "보스 버스"는 **자격은 어렵지만(절대 HP 10%) 뚫으면 전리품 파워가 진짜다.** 시간당 기대
    개수의 정확한 숫자는 파티 사냥 빈도·저레벨 유저의 실제 데미지량이라는 [가정]이 필요해
    이번 감사에서 수치화하지 않았다.

### 5-3. 대안 규칙(D%·k·감쇠) 계산 [코드 없음 - 순수 파생 계산]

이 항목 전체가 **[없음]**(코드에 "직접 잡은 몹" 개념, 거리 반경 R, 레벨 차 감쇠 k, D% 문턱이
전혀 없다 - 현재 코드는 5-2의 단일 10% 문턱뿐이다). 수정 금지 지시에 따라 코드를 만들지 않았고,
**"막타 우회가 막히는지"** 한 가지만 현재 5-2 규칙과 대조해 사실을 적는다: 현재 10% 문턱 자체가
이미 막타 우회를 막는 설계다(막타 1인이 전부 가져가는 구조가 아니라 데미지 비율 문턱이므로,
"남이 깎아 둔 몹에 마지막 한 대"로는 10%를 못 채우면 보상이 없다 - 이미 사용자가 우려한 "버스
우회"가 **현재 규칙에서도 D=10%로 이미 어느 정도 막혀 있다**는 뜻). 사용자가 제안한 D·k·감쇠
체계는 이 10% 문턱을 "직접 잡음"과 "파티 공유"로 세분화하려는 것인데, 세분화된 각 후보(D=10/20/30,
k=10/30/50)의 정량적 효율표는 이번 세션이 만들지 않는다(요청 자체가 "수치만, 설계·구현 금지"이지만
그 수치를 내려면 몹 처치 빈도·파티 구성·저레벨 데미지량 등 다층 [가정]이 필요해 신뢰할 수 있는
숫자를 못 낸다 - 억지로 채우면 근거 없는 표가 된다). **"조건을 만족하는 범위"만 논리적으로
좁힌다**: 5-2에서 확인했듯 현재 10% 단일 문턱이 이미 "정상 파티 손해 없음"(파티원이 정상적으로
싸우면 자연히 10%를 넘는다) + "막타 우회 방지"를 만족하고 있으므로, **새 규칙(D%)의 D는 최소
현재 값(10%)보다 낮춰서는 안 된다**(낮추면 막타 우회 방지가 약해진다)는 것이 유일하게 코드

## 7. 스테이지 도전 조건 [코드]

`server/StageServer.server.lua:43-145`가 유일한 진입점이다.

1. **본인 최고+1 규칙**: `targetStage < 1 or targetStage > best + 1`이면 거절(`"range"`). **건너뛰기
   불가** - 최고 도달 스테이지보다 2 이상 위로는 절대 못 간다. 아래로는 완전히 자유(파밍 유도,
   `best`가 안 내려간다).
2. **보스 게이트**: `targetStage` 바로 아래의 보스 스테이지(`BossRules.getBossStageBelow`)를 아직
   못 깼으면 그 이상 못 간다(`"boss_locked"`). 그 보스 스테이지 자신으로 가는 것(싸우러 가는 것)은
   항상 허용.
3. **파티로 도전할 때 기준**: **오직 파티 리더의 요청만 보스 스테이지 이동을 시작한다** -
   파티원이 보스 스테이지로 이동 요청하면 무조건 거절(`"party_not_leader"`). 리더가 목표
   스테이지로 이동을 요청하면 `BossEncounter.checkPartyEntry(party, targetStage)`가 **멤버
   전원**을 검사(레벨-스테이지 밴드, `BossRules.partyEntryStageCap`)하고, 한 명이라도 막히면
   파티 전체가 거절된다(`"party_blocked"`, 누가 왜 막혔는지 이름까지 리더에게 통지).
4. **파티 클리어 시 각 멤버의 최고 스테이지 갱신** - **리더만 갱신되고, 나머지 파티원의
   `stageProgress.infinite/infiniteBest`는 이 이동으로 바뀌지 않는다.** `performMove()`
   (`StageServer.server.lua:96-125`)는 `PlayerProfile.setInfiniteStage(player, targetStage)`를
   **요청자(`player`, 즉 리더) 한 명에게만** 호출한다 - `BossEncounter.spawnForParty`
   (`server/BossEncounter.lua:459-`)는 멤버들을 텔레포트만 시키고 그들의
   `PlayerProfile.setInfiniteStage`를 부르지 않는다(`grep setInfiniteStage BossEncounter.lua` 결과
   0건). **즉 파티원은 리더를 따라 고스테이지 보스 아레나로 "점프"하지만, 그 사람 자신의 최고
   기록·이후 개인 진행 기준 스테이지는 그대로다** - 오직 보스 처치 보상의 `dropStage`(itemLevel
   기준)만 `monsterData.stageNumber`(보스 스테이지, 전원 동일)를 쓰기 때문에 보상 자체는 고스테이지
   품질로 받되(§5-2), "내가 도달한 최고 스테이지"라는 리더보드용 기록은 오르지 않는다.

## Fable로 넘길 결정 목록

1. **보석 레벨 옵션 곡선 재설계** - 현재 `Option.levelFactor`가 레벨(=몬스터 레벨) 125에서
   완전히 동결된다(5-1). 몬스터 스테이지는 무한히 크는데 옵션 기여도는 정지해 있어, 사용자
   설계 의도("몬스터 레벨이 셀수록 보석도 세진다")를 살리려면 이 함수(또는 별도의 "보석 전용
   레벨 계수")를 새로 설계해야 한다. 숫자 안전성 자체는 문제없다(정지값이라 오버플로 불가) -
   순수하게 "재미·의도" 재설계 문제.
2. **드랍 자격 세분화(D%·거리 R·레벨차 감쇠 k)** - 현재 단일 10% 문턱을 "직접 잡음(감쇠 없음)"과
   "파티 공유(감쇠 있음)"로 나누는 사용자 제안(5-3). 코드 기반 없이 새로 설계해야 하고,
   정량적 검증에는 처치 빈도·파티 구성 등 실측 데이터가 필요하다.
3. **파티 1인당 효율의 "의도된 절반"이 잡몹에서는 반대로 "의도되지 않은 배가"로 나타나는
   비대칭** - 보스는 1인당 효율이 정확히 솔로의 절반이 되도록 설계됐지만(4-4), 잡몹 사냥터는
   보상을 안 나누면서 처치 속도만 합산돼 1인당 효율이 솔로보다 높다. 이 비대칭이 의도인지는
   PRD·README 어디에도 명시가 없어 Fable 판단이 필요.
4. **보스 파티 진입의 "리더만 최고 스테이지 갱신"** - 파티원이 고스테이지 보스를 리더 따라 처치해도
   자기 진행 기록(`infiniteBest`)은 그대로다(7번). 이게 "의도된 설계"(리더보드 축 보호)인지
   "빠뜨린 갱신"인지 코드 주석만으로는 판단할 근거가 부족하다.
5. **측정 도구(`BalanceSim.getSurviveHits`)의 `A²` 부동소수 버그** - 실제 게임(`PlayerDamage.
   computeHitDamage`)에는 없는 결함이지만, `/gg measure`·`/gg curve`가 스테이지 ≈2,448부터
   거짓 결과(생존 0)를 보고한다. 코드 수정은 이 세션 범위 밖이라 보고만 한다 - 다음 계산식으로
   교체하면 해결된다: `dmgPerHit = A * (D/(D+alpha*A) 대신) A*(1 - D/(D+alpha*A))`처럼 제곱을
   피하는 순서.
6. **`NumberFormat.format`의 `inf` 무한 루프** - 스테이지 ≈4,897 이후 화면에 `inf`를 표시하려는
   순간 그 스레드가 멎는다(1-2 ⑤). 실제로 그 스테이지에 도달할 방법이 정상 진행으로는 사실상
   없지만(디버그 명령 제외), 리더보드·PvE 콘텐츠가 계속 확장되면 언젠가 마주칠 수 있는 잠재
   결함이라 기록해 둔다. 최소 수정은 `while scaled >= STEP and scaled < math.huge do`처럼 종료
   조건에 유한성 체크를 추가하는 것.
7. **`MonsterState.lua`의 오래된 주석**(273-275행 "보스는 항상 빈 테이블") - 실제 코드(24-1에서
